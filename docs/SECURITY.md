# Security, provenance and game terms

Never embed, print, log or commit credentials, tokens, game authentication data, personal progress, packet captures or private combat logs. Use synthetic fixtures. Treat anything read from the network or from files as untrusted; upstream validates packet fields before use, and the engine validates paths at its boundary.

Filesystem operations use absolute paths derived from trusted roots (AGENTS.md, "Paths"). The meter writes only under its data directory (per-user by default, the `data` folder beside the exe for a portable copy, or `--data-dir`), apart from the native libraries every single-file .NET app unpacks to `%TEMP%\.net`: history database, settings, logs, the imported background picture and the WebView2 browser profile (ARCHITECTURE.md, "Storage").

`settings.json` is untrusted input: it passes one validation boundary (`SettingsNormalizer`), is size-limited, and can only name a background picture the meter itself imported, so it cannot point the page at another file. A damaged file is kept aside, never deleted; when it (or the backup) cannot be moved aside, or the file comes from a newer build, saving is off for that run so nothing overwrites it (ARCHITECTURE.md, "Settings"). The pages reach local images only through two WebView2 virtual hosts that each map a single folder (the backgrounds folder and the class icons beside the executable), never the database, logs or settings. A Content-Security-Policy allows scripts only from the app and images only from the app, those hosts and NC's game-data CDN, with no plugins. Player names from the network are rendered as text (Blazor escapes them).

`scripts/Smoke-Meter.ps1` opens a WebView2 remote-debugging port on a free localhost port for the duration of a test run only, and drives only pages served from the meter's own origin; the meter itself never enables it. Do not run the script against a data directory holding real data.

Raw packet logging, which upstream offers as a developer setting and which writes other players' data to disk, is not reachable here: the settings bridge reports it off and no packet writer is registered. The history database still stores other players' names and combat statistics for completed boss fights, as upstream does.

## Network

Capture is passive: Npcap reads the game's traffic and the meter sends nothing to the game. The meter's one request of its own is the upstream release check (ARCHITECTURE.md, "Updates"): an unauthenticated HTTPS GET to `api.github.com` for RATmeter's latest release, at most once every six hours while the meter runs (ten minutes after an attempt that got no answer, when GitHub saw no request), carrying a fixed User-Agent and the two headers GitHub's API asks for. It sends no token, no cookies and nothing about the player, the game or combat; GitHub sees the address it comes from and when. Redirects are not followed. The answer is untrusted: only the tag, the release page and the date are read, the tag must be a release tag, the page must be an https page on upstream's repository, at most 1 MiB is read, and the answer's text is never logged. A build that does not know its pinned release sends nothing. A switch in Settings, About turns it off, and then no request is made. The switch lives in `settings.json`: if that file is lost or reset to defaults (an unreadable file is kept aside and defaults are used), or an older build that does not know the `updates` section saves over it, checking is on again. The meter opens a page in the browser only when the player clicks "Release notes", and only an https page under upstream's releases on github.com.

The boss-timers window (ARCHITECTURE.md, "Windows") shows aion2timers.com, a third-party site, only when the player opens it from the overlay's header; nothing loads before. The player reads the page; the meter never reads or stores its content (the site's robots.txt bars crawlers from its API and AI agents altogether, and this is neither). The page runs in a plain WebView2 in its own profile (`webview2-timers`), so its cookies and storage never mix with the meter's pages, with no bridge to .NET (no host objects, no web messages, no injected scripts), no developer tools, no saved passwords or form data, and none of the meter's virtual hosts. Top-level navigations are limited to the site's https pages (`BossTimersSite`); a web page elsewhere goes to the default browser only after the player's click, and only as an http or https address without credentials; other schemes, new windows, downloads, permission prompts, credentials and external protocols are refused. SmartScreen stays on. What the site and the services it loads (ads, analytics) see is what any browser visit shows them: the address the request comes from and the site's own cookies in that profile.

`scripts/Install-Meter.ps1` uses the network only as a build does (NuGet restore); CI's tag step lists and fetches upstream's tags from GitHub. The installer renames and deletes only folders carrying its own marker (or empty ones), never one holding a link, and refuses install paths that overlap the data directory or the checkout after Windows resolves links and short names (ARCHITECTURE.md, "Updates").

## Dependencies

Restore runs with NuGet audit advisories as errors (`-warnaserror:NU1901..NU1904`). Upstream's `AionDpsMeter.Services` at the pinned release pulls the vulnerable native SQLite package (CVE-2025-6965, GHSA-2m69-gcr7-jv3q); Scarlet's root `Directory.Build.props` overlays it with SQLitePCLRaw.bundle_e_sqlite3 3.0.5, mirroring the override the harrynguon/AIon2-Dps-Meter fork carries in its copy of that project (ARCHITECTURE.md, "Upstream overlay"). Upstream itself does not carry it. Audit results are time-dependent, not a security review.

## Public release

Reviewed on 2026-10-25, before the repository was made public and v0.1.0 was published, both later that day (WORKLOG.md):

- **History.** Every file in every commit was searched for credentials (GitHub, OpenAI and AWS token forms, private keys, password and API-key assignments), the builder's home paths, account names and work address, and machine-specific SDK paths: none. No capture, database, log, settings or binary file was ever committed. Commits carry a dedicated GitHub address and the account's public name; the docs name the player by first name, as their author.
- **Licences.** `LICENSE` is the plain GPLv3 text (so GitHub recognises it); Scarlet's notice and RATmeter's credit are in `NOTICE`; THIRD-PARTY-NOTICES.md credits RATmeter, the fork, .NET (with WPF), the Windows SDK projection, the schedule sources and every NuGet package that ships in the program (MIT, Apache-2.0, MPL-2.0 for PacketDotNet with its source location, Microsoft's BSD-style WebView2 licence, public-domain SQLite), all compatible with GPLv3. Binary copies must carry those licences' texts and notices, so the release zip has a `licenses` folder: the MIT text with each holder, the Apache-2.0 and MPL-2.0 texts, every licence and notice file the packages ship (copied byte for byte by `Write-ThirdPartyNotices.ps1`), WPF's third-party notices (pinned to v10.0.13 and checked by hash), and the bundled .NET runtime packs' own licence and third-party notices (copied at publish from the packs used). The exe also bundles Microsoft's Windows SDK projection (`Microsoft.Windows.SDK.NET`, with `WinRT.Runtime`, MIT), which WebView2's composition control needs to draw the see-through overlay (a build without it crashed on start); it is under the Windows SDK licence terms (https://aka.ms/WinSDKLicenseURL), not the GPL, and RATmeter's own builds bundle it the same way. Whether the GPL's system-library exception covers it is a legal question this review does not settle; Harry decided on 2026-10-25 to publish with it, as RATmeter does. `ThirdPartyNoticesTests` fails when the package table is not exactly the shipped packages, a licence cell differs from the package's declaration, a copy differs from its package's file, a named licence has no text, or `LICENSE` is not gnu.org's text byte for byte (SHA-256). The release zip also carries `LICENSE.txt`, `NOTICE.txt`, `THIRD-PARTY-NOTICES.md` and a player's `README.txt`. The complete source, RATmeter's submodule included, is attached to every release as `ScarletMeter-<version>-source.zip` (`Write-SourceArchive.ps1`), since GitHub's own source archives leave submodules out.
- **Game assets.** Class icons and game data are RATmeter's, shipped as RATmeter ships them; skill icons are fetched from NC's site at run time, not shipped. The notices say AION 2's names, art and data are NCSOFT's and that Scarlet is not affiliated.
- **Build.** Releases are built on GitHub's runners by `.github/workflows/release.yml` from a version tag (tests, publish, zip checks, source zip, SHA-256) as a draft, so no developer's paths, account or data can be in them; a maintainer downloads the draft, checks it and publishes it. The build has no debug symbols or documentation files. The workflow keeps the write token away from third-party build code: the job that restores, builds and tests has a read-only token that git does not keep (`persist-credentials: false`), and only a second job, which runs no project code, may create the release. Actions are pinned to release commits (CI too), the tag name reaches scripts only through the environment, and a tag whose commit is not on `main` is refused.
- **Repository rules** (set 2026-10-25, once public, with Harry's go-ahead): the ruleset "Protect main" (no bypass) refuses deleting or force-pushing `main` and any change to it but a squash-merged pull request whose `build-and-test` check passed; "Release tags" lets only repository admins create, move or delete `v*` tags, so no workflow's token can; and workflows from every outside contributor's pull request wait for approval.

A portable build from `Publish-Portable.ps1` (the live copy and its `-Zip` zip) carries no debug symbols or documentation files, so it does not name the builder's folders or Windows account. The zip holds only what the build's manifest lists, never the live copy's `data` folder (settings, history, logs) or anything else the player put there; hand on the zip, never the `portable\ScarletMeter` folder itself, which holds that data. Prefer a release built by the workflow to a zip built on a PC.

The live copy's data sits inside the checkout, in `portable\ScarletMeter\data`, which `.gitignore` excludes (`portable/`); `Publish-Portable.ps1` refuses any other output root inside the checkout. Never `git add -f` anything under `portable\`, and never run `git clean -x` or `-X`, which deletes ignored files and so the player's history and settings.

## Game terms

The fork's assessment at https://github.com/harrynguon/AIon2-Dps-Meter/blob/master/docs/SECURITY.md ("Game terms") applies unchanged: NC's EULA forbids reverse engineering and access outside its published interfaces, and the AION 2 Global Operation Policy sanctions creating or distributing unauthorised programs with an integrated account ban. A passive meter arguably neither circumvents protection nor interferes with operations, but building and running it is the player's risk. Re-read both documents before any public release or any new packet decoding. The repository has been public since 2026-10-25, when v0.1.0 was published, at the player's decision after this review: publishing a build is "distributing" in the policy's words, which ties the publishing account to it more than running it privately did. The README, the release notes and the zip's README.txt say so, and that using the meter is at the player's own risk.
