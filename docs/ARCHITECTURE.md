# Architecture

Scarlet Meter is a .NET 10 WPF application hosting a Blazor WebView. Capture and decoding of the game's traffic are not written here: they come from RATmeter (Kuroukihime/AIon2-Dps-Meter), included unmodified as the `upstream/` git submodule, pinned to release tag **v1.11.5.341** (commit aa3ffc6).

## Data flow

```
network adapters --SharpPcap/Npcap--> upstream CaptureDevice (finds the game's port by its heartbeat)
  -> upstream TcpStreamBuffer (TCP reassembly) -> upstream PacketProcessor (framing, LZ4)
  -> upstream PacketDispatchService -> opcode processors -> upstream EntityTracker + CombatSessionManager
  -> ScarletMeter.Engine UpstreamCombatEngine: GetSnapshot, GetPlayerDetails, GetHistory, GetHistoryFight
     (UpstreamMapping turns upstream's models into Scarlet records; saved fights come from upstream's SQLite store)
  -> ScarletMeter.App MeterPage (polls ten times a second) -> BlazorWebView in the overlay window

Beside the pipeline: upstream TcpStreamBuffer -> ScarletMeter.Engine RecordTap (records upstream does not decode;
  each LZ4 bundle opened once) -> OdyleEnergyTap (Odyle energy), MapLoadTap (the map probe) -> UpstreamCombatEngine

Demo mode (--demo): ScarletMeter.Engine DemoCaptureDevice stands in for upstream's CaptureDevice and runs
  DemoCombatFeed on its own thread -> upstream EntityTracker + CombatSessionManager, called as the opcode
  processors call them; everything downstream is the same.
```

## Upstream boundary

The boundary keeps upstream updates a one-line pin change and keeps Scarlet's own code independent of upstream's internals.

- **Never edit `upstream/`.** It is a submodule; a change there would be lost on the next pin and would fork upstream silently. A fix upstream needs goes to upstream, or to the harrynguon/AIon2-Dps-Meter fork, which carries minimal generic fixes.
- **Releases only.** The pin moves with `scripts/Update-Upstream.ps1 -Tag vX.Y.Z.N`, which refuses anything that is not a release tag. Upstream's `dev` branch is never used.
- **One project references upstream.** `ScarletMeter.Engine` references `AionDpsMeter.Core` and `AionDpsMeter.Services` through `$(ScarletUpstreamRoot)` (src/Directory.Build.props). `ScarletMeter.App` references the engine and `ScarletMeter.WorldEvents` (which references nothing), never upstream. The one other contact is build-time content: the App project copies upstream's class icons (`AionDpsMeter.UI/wwwroot/images/classes/*.png`) beside the executable (see Image hosts). That reads files from the submodule; it adds no code or assembly reference.
- **No upstream type in the engine's public surface.** The app and future modules program against Scarlet's records and interfaces.
- **Build settings do not leak into upstream.** Scarlet's settings live in `src/Directory.Build.props` (imported by `tests/`), never at the repository root. MSBuild imports only the nearest `Directory.Build.props` above a project, so the root file reaches only the upstream projects, which ship none: that file is the upstream overlay (below), nothing else. The build stamp (Updates) is an MSBuild target that `ScarletMeter.App.csproj` alone imports, so it is not an overlay; `BuildInfoTests.OnlyTheAppIsStamped` checks that upstream's assemblies and the engine carry no stamp.

`tests/ScarletMeter.Tests/UpstreamBoundaryTests.cs` enforces the reference rules from the compiled assemblies, the build's dependency graph (every Scarlet project the tests reference, directly or not, except the engine) and reflection over the engine's exported types (base types, interfaces, generic constraints and member signatures). A new Scarlet project is guarded once the test project references it.

## Engine contract

`ICombatEngine` is the whole surface: `Start`, `Stop`, `Reset`, `Capture` (running, adapter name once locked), `GetSnapshot()`, `GetPlayerDetails(playerId)`, `GetHistory(query)`, `GetHistoryFight(fightId)`, `PingUpdated`, `OdyleEnergy` with `OdyleEnergyUpdated` (see "Odyle energy"), `MapId` with `MapChanged` (see "Map probe"), and `PausedInAbyss` (see "Abyss pause"). `CombatSnapshot` is immutable: the active target (name, HP, boss flag), duration, party DPS and one `PlayerRow` per player (identity, class, totals, DPS, damage share, critical rate, deaths). Players the game has not named yet are included with `IsIdentified` false; the UI hides them until they hold over one percent of the damage, as upstream's UI does.

`Start` throws `CaptureStartException` in the two cases upstream fails on: Npcap's `wpcap.dll` cannot be loaded (the message says how to install Npcap), or upstream found no eligible adapter: Npcap listed none, or only kinds upstream skips (Hyper-V, VMware, VirtualBox, TAP, WAN Miniport). Upstream logs nothing about which, so the message names both and suggests running as administrator when Npcap is restricted to administrators. An adapter that is found but fails to open is only logged by upstream, so `Start` can return with nothing listening; the header then stays at "Waiting for the game's connection...".

`Reset` maps to `CombatSessionManager.Reset` only, which runs under the session manager's lock and drops every target's session, the active target and buffered buffs. Upstream's `IPacketService.Reset` is deliberately not called: it also clears the summon-to-owner map (a pet already out would show as an unidentified player) and the TCP reassembly buffer (frames are dropped until the stream re-synchronises), both without a lock while the capture thread writes them, and upstream's own UI never calls it.

Threading: upstream's opcode processors write `EntityTracker` and `CombatSessionManager` on the capture thread. `GetSnapshot` reads the session manager under its lock, but player identities come from `EntityTracker` dictionaries that the capture thread writes outside that lock; upstream's own UI reads them the same way. A racing read can return a stale value or throw; `MeterPage` logs the first failure of a run and retries on the next tick. In demo mode the feed's thread takes the capture thread's place, with the same calls.

`EngineOptions` is host policy: an absolute `DataDirectory` (default `%LocalAppData%\ScarletMeter`, a relative path throws) holding everything the meter writes (see Storage), and `CaptureMode` (`Live`, `None` or `Demo`). `EngineSettings` are the runtime toggles upstream consults on every hit (boss-only capture, grouped summon damage, one-minute dummy mode, history retention); the bridge forwards their `Changed` event to upstream's `SettingsChanged`.

Deliberately unsupported through the bridge: upstream's raw packet logging (`IsPacketLoggingEnabled` is always false and no `FilePacketWriter` is registered) and its buff and skill-cooldown overlays (disabled, so the timed trackers track nothing). Upstream's update checker is not registered.

### Player details

`GetPlayerDetails(playerId)` returns a `PlayerDetails` for a player with damage in the active fight, or null. It is composed from upstream's per-player getters on `CombatSessionManager` (`PlayerStats`, `GetCombatDuration`, `GetPlayerSkillStats`, `GetPlayerBuffStats`, `GetPlayerGraphData`, `GetPlayerCombatLog`), each of which takes the session lock on its own, so like `CombatSnapshot` it is a composition of consecutive reads: a hit landing between two of them can be counted in one part and not yet in another. The active session is compared before and after the reads; if it changed (the fight ended, or the party switched targets), the whole read is taken again, and after three reads that all straddle a change the result is null and the next poll reads afresh. The comparison is by identity, so a switch to another target and back between the two checks goes unnoticed: against several targets at once the parts can, rarely, mix two targets. `PlayerDetailsTests` drives both cases through the engine's internal `BetweenDetailsReads` test seam.

- `Player` is the same `PlayerRow` as in a snapshot; `Rates` are the player's hit rates over direct hits (upstream ignores damage-over-time ticks there). `Duration` is the fight's (first hit by anyone to last), the window over which buff uptime is measured; the row's DPS is upstream's, over the player's own first to last hit.
- `Skills`, by damage: upstream's `SkillStats`. A skill's `Hits` includes its DoT ticks while its flag counts do not, so a ticks-only skill shows 0 for every rate. With summon grouping on, a summon's attacks are folded into the owner skill (the summon's skill whose code belongs to a real class, id above 10); `IsSummonGroup` and `SummonChildren` are set only when more than one skill was folded in, as upstream's own view shows them. `MinHit` is 0 when there is no hit.
- `Buffs`, by uptime: upstream's `BuffStats` over the fight's window, overlapping applications merged; `UptimePercent` is of `Duration`. Upstream orders them by application count; Scarlet orders by uptime.
- `Graph`: upstream's `GraphDataCalculator` output. Seconds count from the player's own first hit, one point per second, `Damage` smoothed over five seconds; buff lanes are merged spans on the same axis.
- `CombatLog`: the newest 1,000 hits (`PlayerDetails.CombatLogLimit`), newest first, with `Second` counted from the fight's start (not the graph's origin), the skill id for filtering, flags, DoT and the summon's name when a summon dealt the hit (usually upstream's placeholder `Player_<entity id>`, since the game does not name summons). Only the log is capped; skills and graph cover every hit.

### History

`GetHistory(HistoryQuery)` maps `CombatSessionManager.GetHistoryPage`: boss fights only (upstream saves nothing else), the running boss fight first with `Completed` false, then saved fights, newest first by end time, paged across both. Training-dummy fights the user has not hit are neither listed nor saved (see "Training dummies"). `HistoryQuery.Validate` is the boundary: page 1 to 1,000,000 (upstream computes the rows to skip as an int, which a larger page would wrap round to the first page), page size 1 to 200, the name trimmed (blank means no filter) and at most 100 characters, `From` not after `To`; anything else throws `ArgumentException` with the rule in its message. Times are local, as upstream records them (`DateTime.Now`): UTC input is converted, unspecified input is taken as local, and returned times are marked local. The name filter is case-insensitive; the date filter matches the fight's end time, both bounds inclusive. Upstream runs the page's database queries under its session lock, which holds up hit processing meanwhile, so the history is read on demand, not on a timer.

`GetHistoryFight(fightId)` returns the whole fight: its entry, every player's row and a `PlayerDetails` per player, computed from the snapshot upstream saved (`SkillStatsByPlayer`, `BuffStatsByPlayer`, `HitsByPlayer` and `BuffEventsByPlayer` through `GraphDataCalculator.Compute`, the log from `HitsByPlayer`) by the same `UpstreamMapping` code as the live view, so a saved fight shows exactly what the live view showed (`HistoryTests` compares them). Saved fights are read from `ICombatHistoryStore.GetSession` directly rather than through `CombatSessionManager.GetHistorySession`, which would decompress and deserialise every hit under the session lock and stall the capture thread for a large fight: a performance choice, which `HistoryTests` checks by loading a saved fight while a held save keeps the session lock taken. Only a running fight goes through the session manager. Loading a large saved fight still takes a while on the calling thread, so the app should call it off the UI thread. Upstream saves a completed fight on a background task, so a fight that has just ended can be missing for a moment.

#### Damaged history

The history database is a file anything can change, and upstream reads it leniently (a missing JSON field becomes its default) or not at all (a column that does not parse fails the read). Neither history call throws for damaged data; both log what they left out.

- A saved fight is cleaned by `SavedFightSanitizer` before it is mapped. Its start and end must be set, in order, at most twelve hours apart; otherwise nothing in it can be timed, and `GetHistoryFight` returns its rows with no details. Within a usable window, it drops null entries, hits with no skill or negative damage, hits more than a minute outside the window, and buff events longer than upstream's decoder accepts (an hour) or outside the window a buff can overlap. It re-sorts hits newest first. Without this, a hit with no time overflowed `GraphDataCalculator`, two hits fifty days apart made a 4.2-million-point graph, and a buff's saved uptime of 1e300 seconds overflowed `TimeSpan`. Uptime is also clamped to the fight's duration. A player whose details still cannot be built is left out of `Details` (logged), not the whole fight.
- A row `GetHistoryFight` cannot read at all (for example text in a date column) returns null, logged.
- Upstream's list query fails on any page that holds such a row (and only on those: other pages still count it). `GetHistory` then reads the list again row by row with `SavedHistoryReader`, skipping and counting the rows it cannot read. The page comes back with `IsComplete` false and without the running fight, which only upstream's query lists.
- The reader makes the same SQLite provider calls EF Core makes for upstream's store (`GetGuid`, `GetInt32`, `GetInt64`, `GetString`, `GetDateTime`). So it skips exactly the rows upstream cannot read and reads the others as upstream does: text in a number column reads as 0, any `State` number is accepted, a numeric date reads as a Julian date.
- It filters as upstream's SQL does: the stored name folded by SQLite's ASCII-only `lower()`, the search lowered in the current culture, compared ordinally. Two differences remain, only for rows upstream itself never writes: dates are compared and ordered as read, where upstream's SQL compares the stored text.
- From then on every page is read that way, so the pages agree. Each call first checks whether upstream's own store reads every row again (`ICombatHistoryStore.GetSessionList`, outside the session lock); once it does, damaged mode ends and that call already goes through upstream's query. So "damaged" means exactly that upstream cannot read the saved list. Any other failure of upstream's query enters the same mode. If even the row-by-row read fails, the page is empty, with `IsComplete` false.
- `SavedHistoryReader` reads upstream's schema (table `CombatSessions`) directly; `HistoryTests` damages rows through upstream's own `CombatHistoryDbContext`, so a schema change shows there.

Upstream's store cannot delete a single fight (only its startup retention cleanup deletes), so the engine offers no delete.

### Training dummies

Upstream counts every training dummy (`isDummy` in its `mobs.json`: the Training Scarecrows, Punching Bags and the like) as a boss (`GameDataProvider.IsBoss`), so every dummy fight is saved to History; and its `ActiveTargetResolver`, once the user's own last hit is over five seconds old, makes the target with the most hits in the last five seconds the active fight, whoever dealt them. Standing by the dummies, other players' fights filled the overlay and History (Harry, 2026-10-26). Scarlet ignores a dummy fight the user has not hit, without editing upstream:

- **The rule** is `DummyFightRule` (pure; `DummyFightRuleTests`): a fight is kept unless its target is a dummy, the user dealt no damage in it, and the meter knows which player is the user. A dummy fight the user hit is kept with every player in it (Harry's choice). `DummyFightFilter` reads the facts from upstream: `Mob.IsDummy`, `PlayerStats.IsUser`, and whether any tracked player is marked as the user (upstream marks the user from the character's info, `PlayerInfoProcessor`, at login). Once known, the user stays known (upstream never unmarks a player), so the tracker's players are read only until then; a read that races the capture thread counts as "not known" for that call.
- **While the user is not known**, every dummy fight is kept, as upstream keeps it. A meter started after login has not seen the character's info and cannot tell the user's fight from a stranger's; hiding them all would hide the user's own. The own bar then has no ring, which is the sign. Once the user is known, a stranger's dummy fight the overlay was showing is dropped at the next poll rather than held.
- **Saves**: `AddScarletEngine` replaces upstream's one `ICombatHistoryStore` registration with `DummyFightHistoryStore` around the store that registration builds, so the session manager's `Save` of each finished boss fight reaches it; a fight the rule leaves out is not saved (logged at Information with the fight's id and the target's name, no player's). Every other call passes through. The registration fails at once (`Single`) if an upstream release registers the store differently.
- **Overlay**: while the active fight is one the rule leaves out, `GetSnapshot` returns the snapshot it returned last, as it stood, as if those hits had not happened, so the user's last fight stays up until the user hits something. (The empty snapshot, the first plan, would have wiped the user's own result five seconds after the last hit whenever someone hit a dummy nearby.) `Reset` clears the held snapshot. A fight without the user that is no dummy fight is held like any other. Since a held snapshot stays up, `GetSnapshot` compares the active fight before and after its reads (the session's identity, and the target's id against it) and reads again when upstream switched between them, giving up with nothing new after three reads, so it never keeps one fight's target with another's players. `GetPlayerDetails` returns null for such a fight, so an open details window keeps its last view, marked stale.
- **History list**: upstream lists running boss fights, dummies included, ahead of the saved ones. `GetHistory` works out how many are running (upstream's count less the store's, which holds finished fights only), reads them as upstream's first page of that size (no saved row is read, so damaged-row handling is unchanged) and checks the dummies' among them (only a dummy's fight is snapshotted, since a snapshot copies every hit under the session lock). With none to leave out, the page is upstream's. Otherwise `PageWithout` repeats upstream's merge without them, the other running fights and then the saved ones from the store, so the count and the pages agree. Unlike upstream's merge it is not one read under the session lock, so a fight that starts or ends meanwhile can be missed, or show, on that one read. `GetHistoryFight` returns null for a running fight the list leaves out; saved fights are never filtered, so one saved while the user was unknown, or before this change, still opens. Reading a running fight's target from the history window's thread races the capture thread's writes; a failed read counts as an unknown target, which keeps the fight.
- **Not covered**: fights saved before this change stay in History (the store cannot delete one). A held overlay is frozen: if the user's party fights on without the user while another player out-hits them on a dummy, the overlay shows the user's fight as it stood until the user's next hit. "The user is known" is any tracked player marked as the user, and "in the fight" is per entity id: if the game gave the user's character a new id without the character's info marking it, the user's own dummy fight would look like a stranger's, hidden and not saved (logged). Whether the game does that is not known (HANDOFF's training-dummy item asks for a check after a teleport).

### Icons

Every `Icon` (`SkillRow`, `BuffRow`, `BuffSpan`, `CombatLogEntry`) is upstream's string, unchanged; the app decides how to serve images.

- Skills and buffs: an absolute URL on NC's game-data CDN, built by upstream's `SkillIconResolver` when `skills.json` is loaded, under `https://assets.playnccdn.com/static-aion2-gamedata/resources/`. An entry of `skill_icons.json` keyed by the code's first four digits wins (`<resources>/<name>.png`, for example `ICON_EL_SKILL_010.png` or `Item/ETC/Icon_Item_Usable_Godstone_WP_r_001.png`); otherwise `ICON_<class code>_SKILL_<NNN>.png` (`_SKILL_Passive_<NNN>` for passives) from the code's digits, or `Icon_Item_Usable_Godstone_WP_r_<hex>.png` for a theostone. It is null where upstream has none (basic attacks, unknown skills). A buff's icon is its skill's. Upstream's own UI downloads these into an `IconCache` folder next to its executable; Scarlet fetches nothing.
- Classes: not exposed. Upstream's class icon is a path into its WPF UI project, from `classes.json` (`/Assets/Classes/<name>.png`), which Scarlet does not ship; the app shows the class icons it copies at build time, by `PlayerRow.ClassId` (see "Image hosts").

### Demo mode

`CaptureMode.Demo` (`--demo`) exercises the whole engine without the game or Npcap. `AddScarletEngine` registers `DemoCaptureDevice` as upstream's `IPacketCaptureDevice`, so upstream's pipeline starts and stops it exactly as it does live capture: `Start` starts the feed's thread, `Stop` and `Dispose` end it and return only once it has ended. While it runs, `Capture` reads capturing on adapter "Demo". The feed (`DemoCombatFeed`) calls only upstream's public API, as its opcode processors do: `EntityTracker.SetSessionPlayerName` for a party of four synthetic players (Demo Gladiator, the user; Demo Cleric; Demo Ranger; Demo Spiritmaster), `RegisterSummon` for the Spiritmaster's fire spirit, `CreateOrUpdateTargetEntity` and `UpdateTargetEntityHpCurrent` for the boss and its falling HP, `CombatSessionManager.ProcessDamageEvent` for hits (critical, back, front, perfect, double and parried; DoT ticks; the spirit's hits), `ProcessBuffEvent` for party and self buffs and `FirePingUpdate` every second. Skill, buff, class and boss codes are real entries of upstream's game data, so names and icons resolve; `DemoRosterCheck` verifies them when the demo starts and in the tests.

Each boss (Aultross, Fediv Wraith and Transcendent Bakarma in turn, all bosses in `mobs.json`) gets HP for 70 to 82 seconds of the party's expected damage; the fight ends when its HP runs out, or after 90 seconds with a last blow by the user. Upstream never ends a fight on a kill: only on a 45-second idle timeout (checked when another target is hit), a respawn, or `CompleteAndPersistActiveSessions`, which is what the engine's shutdown calls. The feed ends each fight through that same public call and then flushes the history store, so each fight becomes one completed history entry; the next starts ten seconds later. A stop abandons a fight in progress (upstream completes it on its idle timeout, as after a real capture stopped), and the next start begins a fresh boss.

A clock jump (sleep and resume, a time change) does not replay or freeze the demo. When the earliest scheduled event is more than five seconds behind or ahead of the step's time, every event moves by the same amount so the earliest falls due now. Before this, one step an hour late replayed 3,600 pings and dozens of fights for over ten seconds, longer than the ten-second stop timeout. The fight in progress carries on from the new time; after a long jump upstream sees a pause in the hits, and from 45 seconds ends that fight and starts another on the same boss, as it would in the game. Each step also checks the stop request between events, so `Stop` is answered within a step.

Demo history goes to `demo-history.db`, never to the player's `combat-history.db`. The feed logs a failing event and carries on, as upstream's packet dispatch does for a failing processor, logging a repeated failure once. Anything that escapes a step is logged and retried; after ten in a row the feed stops and capture reads as off. Upstream's pipeline still counts itself running then, so `Start` does nothing; `Stop` and then `Start` begins a fresh feed. Nothing escapes the thread.

The demo also has Odyle energy (420 basic, 1,200 charged): when the feed begins it hands the engine's `OdyleEnergyTap` a synthetic login list, and each later fight spends 10 basic in a synthetic update (a recharge moves 200 from charged once basic runs low). The records go to the tap directly, not through upstream's stream reassembly (see "Odyle energy" for why), and are never bundled, so they take the same record path as captured ones from there; the login list goes when the feed begins, outside its schedule, which keeps the schedule's order (and a seeded demo's fights) as before.

### Records beside the pipeline

Some records the meter needs are ones upstream does not decode (Odyle energy, the map loaded). Upstream's opcode table takes only processors marked with its internal `PacketOpcode` attribute, so a Scarlet processor cannot join it without editing upstream. Instead one tap, `Upstream/RecordTap`, subscribes to `TcpStreamBuffer.PacketExtracted`, the event upstream's pipeline itself listens to, sees every reassembled record, and hands each one to every `IRecordReader` that takes its opcode (`OdyleEnergyTap`, `MapLoadTap`). An LZ4 bundle (`ff ff`) is opened with upstream's own `PacketProcessor.ProcessPacket`, which is internal and bound once by reflection (`BindBundleOpener`, guarded by a test against the pinned release; without it, or should binding throw, the tap warns and reads only records outside bundles), and each record inside goes to the readers the same way; any other record costs a varint, two byte reads and a question to each reader. A bundle, which most of the game's records come in, is opened a second time after upstream's pipeline has opened it: a full LZ4 decompression into a buffer sized from its header (up to 10 MB for a corrupt one), a list and a copy of each inner record, and upstream logs a broken frame once for each opening (the "CPU and memory" check in HANDOFF covers it; opening bundles in the tap with a pooled buffer would cut it and drop the reflection). It is opened once for all the readers, so a new reader adds no decompression: until 2026-10-26 the Odyle tap listened and opened bundles itself, and the map probe was built by splitting that listening out rather than opening every bundle a third time (`MapProbeTests.OneOpeningOfABundleServesEveryReader`, and `OnlyTheRecordTapListensToTheStream`, which fails if any other engine source subscribes to the stream). The tap runs on the capture thread inside upstream's accumulator callback and lock, so nothing escapes it: an exception thrown back would skip the accumulator's removal of the record, which would then come again with the next chunk, to upstream's pipeline too (its hits counted twice), and one that always throws would stall the stream until the accumulator's 10 MB reset. A reader that throws does not keep the record from the other readers, nor the rest of a bundle from any; a failure (a reader's or the bundle opener's) is logged once until a record is read without one, and once when that happens. A reader's subscriber failing is the reader's own to log, each time.

New connections: a server change (into or out of a dungeon or the Abyss) moves the game to a new connection, which upstream keeps apart by the client's port (`CaptureDevice`'s stream key, `Client:<port>`), each with its own accumulator. An accumulator reads its connection only from its first keep-alive on and drops everything before it (`PacketAccumulator`, v1.11.5.341; its search for the keep-alive also starts at the end of the bytes it holds), so the first records of a new connection can be lost before any reader sees them, the map record among them (LESSONS, "The map probe kept a map after the game changed server"; `MapProbeTests.UpstreamDropsTheMapRecordThatOpensANewConnection` pins it). The tap sees the stream key of each record it reads and tells every reader, just before the first record it reads of a connection it has not seen lately (`IRecordReader.ConnectionStarted`); it remembers the last 16, so a trailing record of the old connection is no new move, and one that falls out of the list counts as new again (the safe side). The map reader forgets its map there; Odyle energy, the character's, is kept. A candidate fix to offer upstream: start a new connection's accumulator reading at its first byte, falling back to the keep-alive search on a bad length.

### Odyle energy

Upstream does not decode the player's Odyle energy, which raids spend; the engine reads it from the same captured stream, beside upstream's pipeline. The records were worked out by A2Tools (taengu/A2Tools-DPS-Meter#63 and its fixes 2723bff and 29e7193, GNU GPL v3; THIRD-PARTY-NOTICES.md, "Code"): the energy is the first entry of the game's list of entry counts, in slot 1. An entry is a kind, a slot, a key and its values, all but the first two as varints, and the kind says which of two values are sent, a zero being left out: `0c` both (`0c 01 <key> <basic> <charged>`), `04` the first only (basic, no charged energy), `08` the second only (charged, no basic energy). Record `0b 61` holds the whole list, at login and after a server transfer, with other data before it, so the entry is found by its shape: a slot-1 entry of any of the three kinds that the list's second entry follows with slot 2 and the same key (in the game's list a one-value entry; a two-value one is taken too). Like A2Tools', the heuristic takes the first such shape. The data before the list opens with a look-alike (`0c 01 00 00 00` in A2Tools' sample), so Scarlet also turns away an entry with a 0 where its kind says a value is: the game never sends one, and A2Tools only bounds the values. Until 2026-10-26 only `0c` was read, with zeros taken: a player with no basic or no charged energy got nothing, and a look-alike could read as `0 (+0)`, which Harry saw. Which one his game sent is not known; two candidates, both modelled on A2Tools' samples and both turned away now: the list's header look-alike backed by a slot-2 look-alike, and an update of the table that header opens, whose id-1 entry reads as kind `0c`, slot 1, key 0, values 0 and 0 (an inference from the samples' shape: that table's entries appear to carry a 4-byte id). Record `0c 61` is a byte and the entries that changed (a recharge item, a raid); a `00` there is not a count to trust (updates that start `00` carry an entry too), so at least one entry is read, and a larger count is kept, so bytes after the entries are never read as more of them. An update can carry another counter's slot-1 entry (A2Tools' list holds one, a one-value count), which would read as the energy, so the tap keeps the energy entry's key from the last list and takes an update's entry only under that key (`OdyleEnergyRecords.ReadEntry`); before any list (a meter started mid-session) it takes the first slot-1 entry, as A2Tools does. How the game writes no energy at all is not documented: such a record gives no value, so the last one stays (the demo starts again from its opening values rather than reach 0 and 0). Each change is logged with the record it came from, the list or an update, never the value or the bytes. A teleport sends neither, so a meter started mid-session shows nothing until the next of them. Values over 100,000 are refused (the game's are 840 basic, 560 without a membership, and 2,000 charged), and so is a varint that does not fit 32 bits. The game's maximum is not in the records, so none is shown.

- **Reading** (`Odyle/OdyleEnergyRecords`): pure and allocation-free over a span; every read is bounds-checked, so malformed bytes give no value rather than an exception.
- **Listening** (`Upstream/OdyleEnergyTap`): a reader on the record tap (see "Records beside the pipeline"), which hands it the `0b 61` and `0c 61` records, plain or from a bundle. A subscriber's failure is logged each time and the rest of a bundle still read.
- **Value**: the latest energy under a lock, kept across `Stop` and `Reset`; `OdyleEnergyUpdated` fires on the capture thread only when it changes. The overlay reads `OdyleEnergy` on its refresh loop rather than from the event, so the two numbers are never read torn.
- **Upstream's stream reassembly**: `PacketAccumulator` (v1.11.5.341) looks for its keep-alive (`0e 00 36`) from the end of the bytes it holds, not the start (`IndexOfArray(pattern, length)`), so a new stream is synchronised only by a keep-alive left from an earlier chunk. Live traffic presumably gets there (the meter reads fights), though how soon is not measured; a one-off injection does not, which is why the demo hands its records to the tap directly and the tests synchronise the stream with a padded keep-alive and then another. A candidate fix to offer upstream.
- **Display**: the overlay's totals line, left of the ping: a crystal of Scarlet's own drawing (not the game's art), the basic energy and, in cyan, the charged in brackets ("420 (+1,200)", `Formatting/OdyleText`), while "Show Odyle energy" (`AppearanceSettings.ShowOdyleEnergy`, on by default) is on and a value has arrived.

### Map probe

The meter learns which map the game has loaded and reports it, which is what lets it pause in the Abyss (below), where hundreds of players fight and upstream keeps every hit of everyone it sees. Built first as a probe so the Abyss's ids could be read off in the game rather than guessed (a wrong id could switch the meter off in a dungeon): Harry's game named the Abyss's lower layer 20 on 2026-10-26 (HANDOFF, "Map probe").

Upstream decodes no map record. A2Tools worked it out (`parse_map_load_packet` in taengu/A2Tools-DPS-Meter's `src-tauri/src/capture/stream_processor.rs`, added in b1fcd53 on 2026-10-05 and unchanged up to 6abf5e7, v2.0.79, read on 2026-10-26; GNU GPL v3; THIRD-PARTY-NOTICES.md, "Code"): record `21 36` is `<length varint> 21 36 <u32> <map id u32> …`, both little-endian, sent on every zone load and naming the map from the game's Map table. A teleport inside an instance names the instance again; leaving names an open-world map. A2Tools calls the first u32 a count (1 on entering, 2 after a teleport inside, in its capture of 36 loads, each 49 bytes with length 52) and does not use it; nor does Scarlet. In A2Tools the id decides which dungeon a fight is filed under: its open-world list (`src/data/open_world_maps.json`, from the game's Map table) and dungeons at 600000 to 699999, an instance's map id being its dungeon id. Its other map records are not used here: the world map's boss list (`01 91`, sent when the player opens the map) names the Abyss's map 20 (and its artifact record a second layer, 22), but whether that world-map id is the id `21 36` sends in the Abyss is not known, which is what the probe is for.

- **Reading** (`Maps/MapLoadRecords`): pure and allocation-free over a span, bounds-checked. Only the id is read, so a record the game lengthens still names its map; a record too short for the id, another opcode, or an id of 0 or past `int.MaxValue` (Scarlet's check; A2Tools takes any value as an i32, and every id it documents lies between 1 and 999,999) gives none.
- **Listening** (`Upstream/MapLoadTap`): a reader on the record tap (see "Records beside the pipeline"), which hands it `21 36` records, plain or from a bundle.
- **Value**: the latest id under a lock, kept across `Stop` and `Reset`, and null while unknown: before the first load read (a meter started mid-session), and after a move to a new connection until a load is read on it. A server change (into or out of a dungeon or the Abyss) is a new connection, and its map record is often lost to upstream's reassembly (see "Records beside the pipeline"): in Harry's game on 2026-10-26 the one entering the Abyss was read, the ones leaving a dungeon and the Abyss were not, and the probe went on showing the Abyss after leaving it (LESSONS). So the map is forgotten at the first record of a new connection (`MapLoadTap.ConnectionStarted`) and logged as unknown; loads on the same connection (a teleport, a world layer for a quest scene, 101014 and 101020 in Verteron that day) are read. A change is logged once at Information as "Map loaded: <id>", the number alone: the rest of the record (undocumented; it may hold a position) is never read, logged or kept. `MapChanged` fires on the capture thread on each change, with null when the map becomes unknown; a load of the same map again (a teleport inside an instance) raises and logs nothing. The demo sends no map.
- **Names** (`Maps/MapNames`, public, pure): a table of 67 names by map id, for the player to read; nothing acts on it. One is seen in the game rather than taken from a source: 503001, the Artifact Corridor, a two-minute instance entered from the Abyss where mobs give Abyss points (its id from the map probe's log in Harry's game, 2026-10-26, between two loads of 20 on the same connection; its name Harry's, 2026-10-27). The open world and the Abyss come from two other meters' data: SkeeveAN/Aion-DPS-Meter (MIT) names the maps of the game's field-boss list by their internal names (World_L_A Verteron, World_L_B Eltnen, World_D_A Altgard, World_D_B Morheim, Abyss_Reshanta_A Chaotic Lower Reshanta, Abyss_Reshanta_C Chaotic Middle Reshanta), and yykk62/AetherDPS (GPL-3.0) gives those internal names their ids (1010, 1011, 1110, 1111, 20, 22). The field-boss list's id for Verteron is what the map-loaded record sends there (A2Tools' capture); for the others that is inferred, as above. AetherDPS also counts 21 as the Abyss, but no source names it, so it has no name. The 60 dungeons are A2Tools' list (`src/data/i18n/dungeons/en.json`), its difficulty in brackets where it gives one ("Krao Cave (Hard)"). Cities and most of the open world are in no source, so the id shows alone; THIRD-PARTY-NOTICES.md ("Data") pins each source.
- **Display**: Settings, About, a quiet "Map" line written by `Formatting/MapText`: the name and the id ("Fire Temple (map 600021)"), the id alone when no name is known ("Map 123456 (no name known)"), or "Not known" (none read yet, or a server change since). The id is written without separators, as the log writes it. The page reads `MapId` when it renders and re-renders the About tab on `MapChanged` (through the renderer's dispatcher), letting go of the event when the window closes. The log keeps the number alone.

### Abyss pause

Harry asked for the meter to switch itself off in the Abyss, and then for the header to say so "like where it says 'Combat'". Asked whether boss fights should still be tracked there, Harry chose: only if that does not still lag; with hundreds of players on one world boss every hit is a boss hit, so it would, and the pause tracks nothing.

- **When** (`Upstream/AbyssPause`): while `EngineSettings.PauseInAbyss` is on (Settings, Tracking, "Pause in the Abyss", on by default) and the last map read is one of the Abyss's (`Maps/AbyssMaps`: 20, Chaotic Lower Reshanta, seen in the game; 22, Chaotic Middle Reshanta, from three sources but not yet seen; AetherDPS's 21 left out until seen). Neither is a dungeon id, so a wrong id here cannot pause the meter in a dungeon. The Artifact Corridor (503001), an instance of two minutes entered from the Abyss, is not paused, at Harry's word: the pause is for the Abyss's crowds, the corridor's load ends it, and the load of 20 on leaving the corridor starts it again. It ends when the map changes or becomes unknown, which leaving the Abyss always does (a server change, "Records beside the pipeline"), or when the setting is turned off. If the map record entering the Abyss is lost, the meter does not pause: it tracks there as before, the safe side.
- **What**: upstream's own boss-only filter is forced on (`UpstreamSettingsBridge.BossOnlyCapture` reads `PauseState`; the player's own setting is untouched), which drops every hit on players and mobs before upstream keeps it; on entering, the fight from before is completed and saved first (`CompleteAndPersistActiveSessions`, as at exit: upstream saves a fight only at a later hit, a new try or exit, so going to the Abyss straight after a kill lost it; deep audit on #42), then the fight is cleared on entering, on leaving and every 2 seconds (`CombatSessionManager.Reset`, which never completes or saves a fight), which drops the boss hits that filter lets through, so nothing piles up and no Abyss fight reaches the history; closing the meter while paused drops the open fight before the exit's save (Codex and the deep audit on #42); the state changes, saves and clears happen under the pause's lock, taken before upstream's session lock and never after it (the boss-only filter reads a volatile flag), so a sweep cannot clear the next place's first hits; and the engine shows nothing (`GetSnapshot` empty, `GetPlayerDetails` null; `ICombatEngine.PausedInAbyss` true), and History lists and opens no running fight (`GetHistory`, `GetHistoryFight`). Pausing and tracking again are each logged once ("Meter paused: in the Abyss (map 20).", "Meter tracking again.").
- **What it cannot save**: capture keeps running, since only the record tap can tell the meter it has left; so upstream still reads and decodes every packet, as RATmeter itself does, and the record tap still opens bundles. Stopping capture would save that, but then nothing could end the pause.
- **Threads**: the map changes on the capture thread, the setting on the UI thread, the sweep on a timer thread; the decision is taken under one lock (reading both the map and the setting there), upstream's reset takes upstream's session lock, and nothing escapes a callback. `PauseState` is its own object so the settings bridge, which upstream's session manager needs, does not depend on the pause, which needs the session manager.
- **Display**: the overlay's header reads "In the Abyss · meter paused" where "No active target" goes (`MeterPage.StatusText`), with no bars or boss card, since the snapshot is empty.

## Windows

Every window is a `ScarletWindow`: a WPF window whose content is one `BlazorWebView` with one root component. The base class sets the WebView2 profile folder and image hosts (below), remembers the window's placement, and applies the deferred close. There is no XAML window; windows are built in code. The meter's icon, `Assets/ScarletMeter.ico`, is the exe's `ApplicationIcon`, and no window sets its own: WPF gives a window without an `Icon` the exe's, taking the system's large and small icon sizes from it, so every window shows it, the boss-timers window and any later one included, with no code to fail. It holds 16, 20, 24, 32, 40, 48, 64, 128 and 256 px PNG entries, every size from the whole of a pixel-art portrait with the meter's bars in a corner (its source: THIRD-PARTY-NOTICES.md, "Artwork").

- **Overlay** (`OverlayWindow`, root `MeterPage`): chromeless (`WindowStyle=None`, `AllowsTransparency`), transparent WebView2 background, always on top, resizable from its side edges only through `WindowChrome` (`ResizeBorderThickness` 6 on the left and right, none on the top and bottom; no caption area). The page paints its own panel; only the panel's `::before` layer takes the background opacity and picture, so text and bars stay solid. The panel is as tall as its content and the window as tall as the panel. ## Settings

`MeterSettings` holds six sections: `Fight` (boss-only capture, on by default for a new install while a saved value is kept; upstream's test is the mob code alone, `Mob.IsBoss` with its HP-threshold fallback commented out, so a target first seen by a hit, with no spawn record and so code 0, or a boss its `mobs.json` does not list, is not a boss and its hits are skipped while the switch is on, which is worth offering upstream as a fix; combined summon damage, one-minute dummy mode, history retention, the Abyss pause; mirrored into the engine's `EngineSettings` on load and on every change), `Appearance` (background opacity 0.1 to 1, background picture, picture opacity 0.05 to 1, class colours, relative bars, show deaths, show combat power, hide names, row size 0.75 to 1.5, skill icons, bar effects and effects on every bar), `Overlay` (the hotkey), `Alerts` (world-event notices), `Updates` (the release check) and `Windows` (placements). A picture's opacity is kept when the picture is removed, so the next picture starts at it (the slider shows again under it). Changes apply live: pages subscribe to `SettingsService.Changed`.

- **Validation** (`SettingsNormalizer`) is the single boundary for both the file and every update: missing or null sections take their defaults, numbers are clamped, the hotkey must parse and is stored canonically, unknown window keys and non-finite or absurd placements are dropped, and the background picture must be a name `BackgroundImages` writes (`background-<8 hex>.<ext>`), so the file cannot point the page at another path. Each repair is logged and shown once in settings.
- **Durability** (`SettingsStore`): `settings.json` in the data directory, at most 1 MB (a UTF-8 byte-order mark from a hand edit is accepted), written to a temporary file that replaces the old one (`File.Replace`), keeping the previous save as `settings.json.bak`. A file that cannot be parsed is renamed to `settings.unreadable-<UTC time>.json` before anything is written, then the backup is tried, then defaults; a missing file with a usable backup restores the backup, and a missing file with a backup that cannot be used protects it as it would the main file, since the second save's `File.Replace` would otherwise overwrite it: a damaged backup is kept aside as `settings.bak.unreadable-<UTC time>.json` before defaults are used, and one from a newer build is used with saving off. Saving is switched off for the run (`CanSave` false, shown in settings) whenever a write could destroy something: a file whose version is newer than this build, a file that cannot be opened, a damaged file or backup that cannot be renamed aside, or a backup that cannot be opened (also when the main file is missing). In that mode the background picture is not changed either, so the protected file's picture stays.
- **Saving** (`SettingsService`): 500 ms after the last change (so a slider drag writes once), and on exit when the host disposes the service. A failed save is logged and shown in settings.
- **Background picture**: picked with the system file dialog, at most 8 MB, copied into `<data dir>\backgrounds` under a content-hash name (the page reloads it when it changes; the original may move), earlier pictures deleted.
- **Hide names** masks every name, yours included, with RATmeter's algorithm (`NicknameMask`), so a masked name reads the same in both meters.

### Image hosts

The pages load images not shipped in `wwwroot` through WebView2 virtual hosts (`WebAssetHosts`), each mapped to exactly one folder so the page can never read the database, logs or settings: `https://data.scarlet.example/` is `<data dir>\backgrounds`, and `https://assets.scarlet.example/` is `assets\` beside the executable, which holds the class icons copied at build time from upstream's `AionDpsMeter.UI/wwwroot/images/classes` (read from the submodule, never edited). `index.html` carries a Content-Security-Policy: scripts only from the app (`blazor.webview.js` and `js/overlay-fx.js`, which need neither eval nor inline script; `RazorMarkupTests` checks every `<script>` loads an app file and none is inline), images only from the app, those two hosts and NC's game-data CDN (for skill icons), no plugins (`object-src 'none'`), `base-uri 'self'`; inline styles are allowed because the pages set widths and colours in style attributes.

## Window lifecycle

WPF disposes a window's WebView2 control when the window closes, but BlazorWebView is never disposed automatically, and a Blazor message sent afterwards terminates the process. `ScarletWindow` therefore cancels its first close, awaits `BlazorWebView.DisposeAsync` on a later dispatcher turn (components first, so `MeterPage.DisposeAsync` stops the refresh loop and unsubscribes from settings and ping events), then closes again. `DeferredWindowClose` is ported from the fork, where the crash was reproduced and the fix is covered by unit tests and a native lifecycle check. The unit tests are ported here (`DeferredWindowCloseTests`); the native check is not yet (see HANDOFF.md).

BlazorWebView 10's `DisposeAsync` disposes the components and then the WebView2 composition control on whichever thread the component disposal completed on; the control refuses cross-thread COM access with an `InvalidCastException` (E_NOINTERFACE). `ScarletWindow.ReleaseBlazorContentAsync` catches that and disposes the control again on the UI thread, which succeeds; both steps are logged at Information. The fork's companion window logs the same failure, so the fallback is a candidate fix to offer it.

Shutdown order: tool windows close (deferred, awaited), the overlay closes, `App.OnExit` disposes the engine (stops capture, completes open fights, flushes history), then the host.

Startup failures: any exception while creating the data directory, building the host, constructing upstream's graph (game data, history database) or showing the window ends in a "could not start" dialog and exit code 1; a failed capture start gets its own dialog. Once the host exists the failure is also logged at Critical (Error for capture). Before that (bad arguments, a data directory that cannot be created) there is no log file, and the dialog is the only report. Unhandled exceptions on the UI thread or elsewhere are logged at Critical, not handled, so the process still terminates.

## Storage

Everything the meter writes lives under `EngineOptions.DataDirectory`, which `App` chooses at start: `--data-dir` when given; else, for a portable copy (`PortableLayout`: a `ScarletMeter.portable` marker beside the executable, in the application's base directory, never the working directory), the `data` folder beside the executable; else `%LocalAppData%\ScarletMeter`. A portable copy that cannot create its `data` folder stops with a message naming it, instead of falling back elsewhere. `scripts/Publish-Portable.ps1` writes the marker and carries the `data` folder, with anything else the build did not put there, into each new build; an installed build never has one (CI checks both).

- `combat-history.db`: upstream's EF Core SQLite store of completed boss fights, retention per `EngineSettings.HistoryRetentionDays`.
- `demo-history.db`: the same store for `--demo` runs, so synthetic fights never mix with real ones.
- `logs/scarlet-<date>.log`: Serilog, 14 days.
- `settings.json`, `settings.json.bak` (the previous save), and any `settings.unreadable-<UTC time>.json` kept from a damaged file (see Settings).
- `backgrounds/`: the imported background picture.
- `webview2/`: the WebView2 browser profile (cache, local storage, GPU cache; no meter data). `ScarletWindow` sets it through `BlazorWebViewInitializing`; otherwise BlazorWebView would use `%LocalAppData%\ScarletMeter.WebView2` and `--data-dir` would not isolate a run.
- `webview2-timers/`: the boss-timers window's own WebView2 profile, with aion2timers.com's cookies, storage and cache (the site's own choices, such as server and faction); kept apart from the meter's pages (a Windows-wide `WEBVIEW2_USER_DATA_FOLDER` would override both folders; SECURITY.md). Deleting it resets the site's choices.

Nothing is written next to the executable or in the working directory. Upstream's `appsettings.user.json` is not used.

## World events

`src/ScarletMeter.WorldEvents` holds the schedule behind the overlay's world-event notices: the built-in rules, their validation, the occurrence calculation and the alert planner. It is ported from the World Companion of the harrynguon/AIon2-Dps-Meter fork (`AionDpsMeter.Companion/wwwroot/schedule.mjs`, `presets.mjs` and `state.mjs`, JavaScript, at 4feb72b), together with its tests; the alert planner is new. The overlay's notices use it (Overlay notices, below).

The module is pure .NET and independent: it references no project in this repository, no upstream assembly, no UI framework and no package (`WorldEventsBoundaryTests`), so it can move to another meter unchanged. Storage, the settings format and every other host policy belong to the host. Nothing in it reads the system clock or the PC's time zone: the current instant and the server offset are parameters, instants are compared in UTC and every instant it returns is UTC (offset zero).

| Type | Purpose |
| --- | --- |
| `EventRule` | Immutable rule: `Id`, `Name`, `Location`, `Kind` (`EventKind`: Boss, Rift, Event, Reset), `Basis` (`ScheduleBasis`: Utc, Server), `Days` (null = every day; 0 = Sunday to 6 = Saturday), `Hours`, `Minute`, `DurationMinutes`, `EntryMinutes?`, `ActiveMinutes?`. `Hours` and `Days` are copied, de-duplicated and sorted on construction (and by `with`) and compare by value. Ranges are not enforced on construction, so a host can build rules from untrusted settings and validate them. |
| `EventIds`, `EventCatalog` | The nine ids (`shugo`, `invasion`, `rift`, `siege`, `kaira`, `nahma`, `executors`, `daily`, `weekly`, the fork's strings) in display order, which is Scarlet's (the fork starts with Kaira), the siege named Abyss Siege (the fork's Artifact Siege), both Harry's choice for the event row; the presets `Legacy` and `Global`, with `Default` = `Global`; `DefaultServerOffset` (UTC+9); `TryApplyOverrides`. |
| `ScheduleValidation` | `ValidateRules` and `ValidateServerOffset` return `ScheduleError(RuleId, Message)` lists, empty when valid. |
| `EventSchedule` | `Occurrence(rule, now, serverOffset)` returns an `EventOccurrence`; `Timeline(rules, now, serverOffset)` returns them all, ordered. |
| `AlertPlanner` | `Plan(rules, enabledIds, now, serverOffset[, leadTime])` returns an `AlertPlan`: the `EventAlert`s to show and when they next change. |

### Occurrences

- An occurrence starts on each listed weekday at each listed hour and `Minute`, read in the rule's clock: UTC, or UTC plus the server offset. The offset is fixed, so a region with daylight saving needs it changed by hand, as in the fork. A start at exactly `now` has begun; a window or entry window that ends at exactly `now` has closed.
- The window runs from the start for `ActiveMinutes ?? DurationMinutes`. A duration of 0 is never active: resets, and the boss and siege windows of the Global preset, whose end times are unknown. The entry window is `EntryMinutes`, or a rift's `DurationMinutes` (the portal).
- `EventOccurrence`: `Phase` (`Upcoming`, `PortalOpen` for a rift's entry window, `EntryOpen`, `ActiveEntryClosed`, `ScheduledActive` for a window without an entry window), `IsActive`, `IsEntryOpen`, `Start` (the running occurrence while active, otherwise the next one), `Next` (the first start after `now`), `End`, `EntryEnd`, `TargetEnd` (the entry close while entry is open, the end while otherwise active, else the next start), `Remaining` (to `TargetEnd`, always positive) and `Progress` (0 to 100: elapsed share of the countdown while active, share of the final hour while upcoming).
- `Timeline` orders active occurrences first, then by `Remaining`, then by id, and keeps simultaneous events. The id tiebreak is ordinal; the fork's `timeline()` uses `localeCompare`, which gives the same order for the catalog's lowercase ASCII ids.
- `Occurrence`, `Timeline` and `Plan` throw `ArgumentException` for a rule that fails the value checks below and `ArgumentOutOfRangeException` for an invalid server offset: validated input is their precondition. They also throw `ArgumentOutOfRangeException` when an instant to return lies outside `DateTimeOffset`'s range: the next start for a `now` within a week of `DateTimeOffset.MaxValue`, or the start of a window still running within a day of `DateTimeOffset.MinValue` (both presets work at `MinValue` itself). No real clock gets there.

Deliberate differences from the fork: `End` and `EntryEnd` belong to the occurrence at `Start`, so they lie ahead for an upcoming event (the fork's `end` belonged to the most recent start, in the past for an upcoming event; its UI never read it). Minutes are whole numbers and the server offset is a whole number of minutes (the fork accepted any finite number; whole minutes keep the offset usable as a `DateTimeOffset` offset). Validation returns every problem rather than throwing at the first.

### Validation and saved rules

`ValidateRules` makes the checks of the fork's `validateEvents` and `validateState`: each of the nine ids exactly once (missing, duplicate and unknown entries are reported), a defined clock, hours 0–23 (at least one), days 0–6 (at least one) or null, minute 0–59, duration 0–1440, entry window 0 to the duration, activity from the duration to 1440, and an activity length for the rift. Kinds come from the catalog, never from the input. Unsorted or repeated hours and days are not errors, since rules normalise them. `ValidateServerOffset` accepts −12:00 to +14:00 in whole minutes, so +5:30 and +5:45 pass. Each error names the catalog id it concerns, or null for list-level problems and unknown ids; input text is never copied into an error. The work and the result are bounded for hostile input: a list of more than `MaximumEntries` (twice the catalog, 18) gets the single error "too many entries", and at most `MaximumReportedErrors` (50) errors are returned, the last saying that more exist. The size of the file the rules come from is the host's to bound before it deserialises.

`TryApplyOverrides(saved, out rules, out errors)` is the fork's `validateState` merge: when the saved rules pass, it returns them in catalog order with the catalog's id, name, location and kind, taking only the clock, days, hours, minute, duration and entry window from the saved rule, plus the activity length for the rift (a saved activity length on any other entry is dropped). On failure the host decides: reject the file (the fork runs on defaults and blocks writes until the player recovers) or repair the named entries, for example from `EventCatalog.Default`. File versioning stays with the host's settings format.

### Alert planner

`AlertPlanner.Plan` gives each enabled rule at most one alert:

- **Open** while its portal or entry window is open, from the start (inclusive) to the close (exclusive). `Deadline` is the close. Resets never get it.
- Otherwise **Soon** while its next start is at most the lead time away, from exactly start minus lead time (inclusive) to the start (exclusive). `Deadline` is the start.
- Nothing else: an event that is active without an open entry window (a legacy boss or siege window, or a Shugo or Invasion window after entry has closed) gets no alert, though its next start still gets Soon. While Open shows, it hides a Soon for the same rule.

Each `EventAlert` carries the rule, `Kind`, the occurrence's `Start`, the `Deadline` and `Remaining` (to the deadline). Alerts are ordered Open first, then by earliest deadline, then by id. The lead time defaults to five minutes (`DefaultLeadTime`) and must be 1–60 minutes, otherwise `ArgumentOutOfRangeException`. Rules whose ids are not in `enabledIds` are skipped without being checked.

`AlertPlan.NextChange` is the first instant after `now` at which the alerts differ: one appears, disappears or moves to another occurrence. Before it only the countdowns move, so the overlay can show the alerts, count down to each deadline itself and call `Plan` again at `NextChange` rather than every second. Per rule it is the close or the next start, whichever is first, while Open shows; otherwise the next start minus the lead time while that is ahead, else the next start. It is null when no rule is enabled. A test walks eight days minute by minute for both presets and checks that the plan is constant up to `NextChange` and different at it. Planning allocates nothing when there is no alert, and one or two small arrays otherwise.

The icons wrap onto a second line rather than run out of a narrow meter (at the narrowest, 300 px, once three are lit, a lit icon's minutes and seconds making it 58 px; at 360 px three lit fit one line). Clicking an icon opens its detail line under the row: the name and "in 4:59" before a start, with a progress line filling over the lead time; "Portal open · 7:12 left" or "Entry open · 2:10 left" while entry is possible, its line emptying; for one not due its status and the time to its next start ("next 21:00 · in 2 h 14 m"). Clicking another icon opens its line too, the lines in the row's order whatever the clicks' order, and clicking an icon again closes its own; which lines are open is the row's own state, not saved, and each line is keyed to its event's state and occurrence so a new progress line starts afresh. The row never scrolls: the window grows by the line when it opens, and at the screen's height the lowest rows give way instead. A bell in the overlay's header turns the notices off or on in one click (the same `AlertSettings.Enabled` as Settings, Alerts, saved; struck through when off; its accessible name stays "World-event alerts" with `aria-pressed`), and with "Hide during boss fights" on (`AlertSettings.HideDuringBossFights`, the default) the row stands aside while a boss fight is under way (`EventRowLayout.HiddenForFight`, from `Combat/BossFightHold`). The hold follows the boss rather than the current target, since upstream's target is whatever the player hit last and flips between a boss and its adds: it starts when a boss is the target, lasts while that boss's HP moved within the last 60 seconds whichever target is current, and ends when the boss is seen at 0 HP, when the target goes (a reset, or a kill the engine drops), after 60 seconds of still HP (a wipe, or a boss left alive, which upstream keeps as the target until the next hit), or when the clock goes back (the time since the last move cannot be known, so it lets go until the next hit); a still boss holds again once its HP moves or it becomes the target again after another boss or none. The 60 seconds are not verified against the game's invulnerable phases. While held, the row stays mounted but empty, its screen-reader summary included, so a notice that came due during the fight is announced when it ends. Each icon's accessible name is its event and what it is doing ("Shugo Festival, starts 21:00"), and it says whether its line is open; the tip is for the eye only. Screen readers hear a hidden summary ("Shugo Festival starts at 21:00") that changes only when a notice appears or changes kind, not the per-second countdown.

- `Alerts/AlertMonitor` (singleton) computes the view from `AlertSettings` and the clock (`TimeProvider`), and sleeps until the plan's `NextChange` plus 20 ms, never more than a minute, so a sleep, resume or clock change is corrected within a minute. It raises `Changed` (the overlay and the settings window's Alerts tab re-render) and `EventApproaching` once per event occurrence, when its Soon notice first appears. Announced occurrences are kept until they start, so switching an event off and on or changing the lead time does not announce one again. A failure in the computation or in a subscriber is logged and never thrown into the timer thread or the settings caller; after a failed computation the view is empty and the monitor tries again a minute later. `Start` is idempotent and does nothing after `Dispose`.
- Countdowns are the page's: `MeterPage` passes the current time to the row on every 100 ms render.
- `MeterWindows.FollowAlerts`: on `EventApproaching`, if the meter is minimized and the player opted in (setting "Bring the meter back before an event", off by default so a hidden meter stays hidden), it is shown again with `ShowWindow(SW_SHOWNOACTIVATE)`, so the game keeps keyboard focus. That is once per occurrence, never for an Open notice. Owned tool windows come back with it. While the notices stand aside for a boss fight (the overlay reports it on every refresh through `IMeterWindows.HoldAlerts`), the restore waits and happens when they come back, only if a notice is still due then (`Alerts/AlertRestoreGate`).
- `AlertSettings` (settings.json `alerts`): on/off, lead time 1 to 60 minutes (default 5), the alerted event ids (default: the world events and bosses, not the resets), the server UTC offset in whole minutes (default +9), the next event's time on its icon (off) and bringing the meter back (off). The normalizer keeps only catalog ids, once each, in catalog order (`DefaultEvents` is already in it). The old strip's `noticesExpanded` is gone; a file that has it loads, the value passed over. The schedule itself is always the catalog's Global preset; per-event time overrides (the module's `TryApplyOverrides`) are not in the settings yet.
- The settings window's Alerts tab lists each event with its schedule ("Every 3 h from 02:00 server time · portal 10 min") and its state in the PC's local time (`EventText.Status`): "next 21:05", "next Sun 22:00" when not today, "portal open now", "entry open now", "running, entry closed", or "started 21:00" for a window without entry. It shows no countdown, since it re-renders only when the monitor wakes (at least once a minute). It repeats the accuracy warning below.

**Accuracy: not verified against Global Asia / Nezekan.** UTC+9 is an assumption. The fork's evidence (its HANDOFF.md) is consistent with the preset but proves no exact transition: a daily-completion countdown consistent with 16:00 server (07:00 UTC), the player's report of the weekly reset at Wednesday 18:00 Melbourne during AEDT (07:00 UTC), and two rift reports, rounded to the minute, at about 08:00 and 11:01 server. Entry closures (Shugo and Invasion after 3 minutes, the rift portal after 10), boss and siege times, and resets outside Australian daylight saving are unobserved. A scheduled window is not a live report: a boss may already be dead. The A2Tools reproduction cases of the fork's TIMER-COMPARISON.md are tests here; passing them shows agreement with A2Tools' arithmetic, not with the game. In-game verification is listed in HANDOFF.md.

## Updates

There is no self-updater. RATmeter's updater downloads a published release and replaces its own executable; Scarlet Meter's releases (GitHub Releases, built by `.github/workflows/release.yml` from a version tag, DEVELOPMENT.md "Releases") are a zip the player extracts into the folder holding the old copy, which keeps its `data` (each release also carries the licence texts and notices in `licenses/`, and its complete source, RATmeter included, as a second zip from `Write-SourceArchive.ps1`), and a checkout updates itself by building, which keeps the build, the tests and the audit-as-errors restore. What changes for the player is upstream: a game patch breaks decoding until upstream releases parser fixes, and the meter gets them when the submodule pin moves. Updating is therefore: notice the release, move the pin (`scripts/Update-Upstream.ps1`), rebuild and reinstall (`scripts/Install-Meter.ps1`). Commands are in DEVELOPMENT.md ("Install and update").

- **Build stamp.** `src/ScarletMeter.App/Updates/BuildStamp.targets` runs before the SDK generates the assembly attributes and stamps two `AssemblyMetadata` entries into the app: `ScarletUpstreamRelease`, the tag naming the submodule's commit (`git describe --tags --exact-match` in `$(ScarletUpstreamRoot)`), else the submodule's short commit, else `unknown`; and `ScarletCommit`, Scarlet's short commit, else `unknown`. A missing git, repository, submodule or tag changes the value and never fails the build. The target runs on every build; the SDK hashes the attributes, so only a changed value recompiles. `BuildInfo.Current` reads the stamp. A clone made with `--recurse-submodules` has upstream's tags; CI's shallow submodule clone lacks the pinned one, so CI fetches it first (DEVELOPMENT.md, "CI").
- **Release check.** `UpstreamReleaseChecker` (behind `IUpstreamReleaseChecker`, registered by `AddUpstreamReleaseChecker`) asks `https://api.github.com/repos/Kuroukihime/AIon2-Dps-Meter/releases/latest` for upstream's latest release and compares it with the stamp. It reads only `tag_name`, `html_url` and `published_at`. The tag must be a release tag, `v` and four numeric parts (ASCII digits, nothing after), compared as numbers, so v1.10.0.1 is newer than v1.9.4.277. The page must be an https page under `https://github.com/Kuroukihime/AIon2-Dps-Meter/`, with no query, fragment or percent-encoding, so the UI can open it. The result is `UpToDate`, `NewerAvailable` (tag, page, publication date) or `Unknown` (an `UpstreamReleaseCheckFailure` and a one-sentence reason: pinned release unknown, timeout, network, rate limit, 404, other HTTP status, invalid answer, cancelled by the caller or by the meter closing, unexpected). It never throws to callers; failures are logged as warnings with the reason only, never GitHub's text. The last result is cached in memory, not on disk.
- **Network footprint.** At most one unauthenticated HTTPS GET to api.github.com every six hours per process once GitHub has answered (a release, a rate limit, a 404 or an invalid answer alike), timed from the start of the previous request; after a request that got no answer (no connection, or no reply within the timeout) the next may follow ten minutes later, so a meter started offline still learns of a release that session. GitHub counts no request it never answered, so the retry cannot worsen a rate limit. Concurrent callers share one request. The request carries a fixed User-Agent, `Accept: application/vnd.github+json` and `X-GitHub-Api-Version`: no token, no cookies, nothing about the player, the game or combat. Redirects are not followed, the timeout is ten seconds and at most 1 MiB of answer is read. A build stamped with a commit or `unknown` sends nothing, and nothing is sent until the UI calls `CheckAsync`. `App.xaml.cs` registers it and `UpdateNotice` (below) is its only caller; with the settings switch off no request is made at all.
- **Notice.** `Updates/UpdateNotice` (singleton, started once the overlay is open) asks the checker 30 seconds after start-up, so launching is not slowed, and again when the checker's cached answer expires: six hours after an answer, ten minutes after none, plus five seconds. It only schedules and remembers; a checker failure that escapes anyway is logged and retried ten minutes later. While `UpdateSettings.CheckUpstreamReleases` is on (the default) and the latest release is newer and not the one the player dismissed (`DismissedRelease`, a release tag; the normalizer drops anything else), the overlay shows one quiet line above the event row: "RATmeter v… is out", "Release notes", and a cross that hides it until the next release. Settings, About shows the release the build is on, the last result in plain words, and, when one is out, the two commands that update the meter, rooted at a `<checkout>` placeholder as DEVELOPMENT.md writes them. `MeterWindows.OpenReleasePage` hands the shell only an https page under upstream's releases on github.com, with no port, credentials (not even an empty `@`), query or fragment (`IsUpstreamReleasePage`), however the checker validated it; `Uri` resolves dot segments, percent-encoded ones included, before the prefix check. A check never starts while the switch is off or after the meter began closing, even from a timer callback already on its way, and a check in flight when the switch goes off books no other.
- **One-command update.** `scripts/Update-Meter.ps1` finds RATmeter's latest release, refuses while the meter runs from the portable copy, and in a temporary worktree on a local branch `update/upstream-<release>` moves the pin (`Update-Upstream.ps1`), commits it, and updates the portable copy `<checkout>\portable\ScarletMeter` in place (`Publish-Portable.ps1`); the checkout's files are untouched, and a reused branch must contain HEAD (DEVELOPMENT.md, "Update the portable copy in one command"). Settings, About shows that one command for a portable copy.
- **Portable.** There is one portable copy, `<checkout>\portable\ScarletMeter` by default, already unzipped, so the player always runs the same `ScarletMeter.exe`. `scripts/Publish-Portable.ps1` builds, tests and publishes the same self-contained single-file build into `ScarletMeter.staging`, checks it, lists its top-level files in a manifest (`.scarlet-portable-files`) and adds the portable marker, then swaps it in by renames on one drive: the copy becomes `ScarletMeter.old`, everything in it the old manifest does not list (the player's `data` folder and anything else they put there) moves into the new build, the new build takes the copy's name, and the old build's files are deleted. A failed rename is undone (or, when an undo fails, left for the next run to finish, with a message saying where everything is), a run cut short is finished or undone by the next one (and a restore cut short is resumed, the copy keeping its staging marker until the player's files have all followed), only files a manifest lists are deleted, markers go last so a cut-short delete stays recognisable, only folders carrying its markers (or empty ones) are renamed or deleted, and links are refused. One run per output root at a time (a named mutex). `-Zip` also writes the build, never the player's files, to `ScarletMeter-win-x64.zip`; earlier stamped builds holding only a build's files are removed (DEVELOPMENT.md, "Portable build"). The folder rules are `scripts/PortableFolders.ps1`, built on `InstallFolders.ps1`'s path helpers, and `scripts/Test-PortableFolders.ps1` checks them on throwaway folders. The build carries no PDBs or XML documentation files, so it names nothing of the builder's folders. `Install-Meter.ps1` refuses folders holding `ScarletMeter.portable` or `data` (`Assert-InstallFoldersOwned`). Settings, About shows `Update-Meter.ps1` in place of `Install-Meter.ps1` when the running meter is portable.
- **Install.** `scripts/Install-Meter.ps1` builds Release with the tests, publishes self-contained single-file win-x64 into `<install>.staging` beside the install (default `%LocalAppData%\Programs\ScarletMeter`), checks it with `Test-PublishLayout.ps1`, writes the install marker `.scarlet-install` (fixed text) into it and swaps folders by renames, keeping the old install as `<install>.previous` for a manual rollback. If a rename fails, each earlier one is undone on its own and the error lists where every folder is. It renames or deletes only folders that carry its marker, or are empty, and none that holds a link; it refuses paths that are not on a local drive (UNC, admin shares, `\\?\`, `\\.\`) and install folders overlapping the data directory or the checkout, compared after Windows resolves links, junctions, 8.3 names and substituted drives (`GetFinalPathNameByHandle`) in the install's parent and, when it exists and is not a link, the install folder itself. It refuses while the meter runs from the install, and never touches the data directory. Deletes remove the marker last, so a delete stopped by an open file leaves a folder the next install still recognises. The folder rules live in `scripts/InstallFolders.ps1`, which the installer dot-sources. `scripts/Test-InstallMeter.ps1` checks the refusals with `-CheckOnly`, which builds and moves nothing, and runs the delete and swap paths from that library on fake install folders: a `.retired` held open keeps its marker and blocks the swap, then goes once released, and a failed rename is undone.
